## Method

- `analysis/ligature/reverify.py --slow` drove the whole run. It `rsync`s the
  workspace to a scratch root and **resets the scratch to the pristine baseline
  before every single `repro_cmd`**, so no repro inherits another's mutation. That is
  load-bearing, not hygiene: `date-ligature-041` leaves
  `specs/_closure/date-creusot-core.json` with `closure_kind: "degraded"` and
  `date-ligature-047` rewrites `ci/results/feature_ledger.json`
  (see `date-creusot-053`). The live pilot root was never written to by the harness.
- Documented substitutions: the absolute workspace prefix is rewritten to the scratch
  root; a repro that uses `date-creusot` **as a directory** runs with the workspace
  root as cwd and one that uses bare `tools/ligature/...` / `specs/...` / `rust/...`
  paths runs with the pilot root as cwd; nix repros are wrapped in
  `nix develop "path:<scratch>#date-creusot" -c bash -lc '...'`, the explicit `path:`
  ref that #88/#89 documented for this workspace.
- Binary under test, verified **before anything else ran**:
  `sha256sum -c tools/ligature/SHA256SUMS` -> `ligature.pyz: OK`, sha256 `3edfd03cd4e6dee30139c48e7921abcf338cb279ff2eb4e4d0bba9a44725deb4`,
  `ligature version` -> `ligature 1.1.1`, adjudicator `zipapp (attested: true)`.
- Per-id machine record: `reverify-results.json` (regenerated next to this file from
  `reverify.py`'s `results.json`). This file is generated by
  `reverify-verdicts.py`; the bucket counts below are derived from the per-finding
  table, so they cannot drift from it.

## Two harness notes a fresh agent needs before re-running this

Neither is a ligature defect and neither is a finding; both are properties of this
issue's own harness, and both cost a full run to discover.

1. **`TMPDIR` must be a directory that outlives the launcher.** `nix develop` creates a
   temp file in `$TMPDIR` before it evaluates the flake. A harness launched from a shell
   whose `TMPDIR` is later removed makes **all 14 nix repros fail identically and
   instantly** (`error: creating temporary file '<tmp>/nix-shell.XXXX': No such file or
   directory`, exit 1, in ~2.4s each), which reads exactly like a clean finding table
   of failures. That is what the first attempt of this run produced.
2. **`REVERIFY_ROOT` is read, never exported.** `reverify.py` line 45 does
   `os.environ.get("REVERIFY_ROOT", "/tmp/opencode/reverify-8c")`, so a command that
   references `$REVERIFY_ROOT` -- including `date-creusot-054`'s own `repro_cmd` -- sees an
   empty string. Export it yourself before running that finding by hand.
